# Rollback procedure — `20260824120000_canonical_customer_and_deletion.sql`

Read this before applying the migration to production. It is not itself a
migration and is never executed automatically.

## Transaction shape — read this first

**The migration is NOT one atomic transaction.** It is ten sequential
`begin; … commit;` blocks:

| # | Block | Reversible? |
|---|---|---|
| 1 | canonical FK columns + indexes | yes — drop column |
| 2 | invoice Storno columns | yes — drop column |
| 3 | customer archive columns + index | yes — drop column |
| 4 | **backfill (data)** | **only from a backup** |
| 5 | `owner_customer_delete_blockers` | yes — drop function |
| 6 | delete / archive / unarchive RPCs | yes — drop function |
| 7 | `owner_cancel_invoice` | yes — drop function |
| 8 | `owner_link_invoice_customer` | yes — drop function |
| 9 | `owner_list_customers`, `owner_customer_detail` (REPLACE) | yes — restore prior body |
| 10 | grants | yes — implicit with the drops |

A failure in block *n* leaves blocks 1…*n−1* committed. That is deliberate and
safe here because **the migration is idempotent and re-runnable** (verified: two
consecutive applications produced no duplicate customers and no changed links).
The normal recovery from a partial failure is therefore *fix and re-run*, not
rollback.

Blocks 1–3 and 5–10 are structural and fully reversible. **Block 4 is the only
one that writes data**, and it is:

- insert-only for new customers (steps d, e);
- `NULL`-only for every `update` (a, b, c, e–g) — no non-`NULL` value is ever
  overwritten;
- it never deletes and never truncates.

So even block 4 destroys nothing. Reversing it means removing links the
migration added and deleting customers it created — the script below does that,
but see the warning.

## Backup

Confirm in the Supabase dashboard before applying
(**Database → Backups**, project `lqgtmoulqzmrhglabrms`, region `eu-central-1`):

1. the date of the most recent daily backup;
2. whether Point-in-Time Recovery is enabled (PITR is a paid add-on; on the
   current plan it is most likely **not** available — branching already proved
   this project is below Pro).

If neither exists, take a manual dump immediately before applying:

```bash
npx supabase db dump --db-url "postgresql://postgres:[PASSWORD]@db.lqgtmoulqzmrhglabrms.supabase.co:5432/postgres" -f pre-canonical-customer.sql
```

Given the size of the affected dataset (**1 customer row created, 8 records
linked**), a targeted dump of the five touched tables is enough and far faster
to restore:

```bash
pg_dump "postgresql://postgres:[PASSWORD]@db.lqgtmoulqzmrhglabrms.supabase.co:5432/postgres" \
  -t public.owner_customers -t public.owner_invoices -t public.owner_payments \
  -t public.owner_subscriptions -t public.owner_expenses -t public.owner_offers \
  --data-only -f pre-canonical-customer-data.sql
```

## Rollback SQL

> **Do not run this once the new schema is in use.** After the application has
> begun writing `owner_customer_id`, dropping the column discards real
> relationships that were never in any backup. Past that point the correct move
> is to fix forward. This script is for the window between applying the
> migration and putting it to use.

```sql
begin;

-- 10/6/7/8/5 — drop the RPCs this migration introduced.
drop function if exists public.owner_delete_customer(uuid);
drop function if exists public.owner_archive_customer(uuid);
drop function if exists public.owner_unarchive_customer(uuid);
drop function if exists public.owner_cancel_invoice(uuid, text);
drop function if exists public.owner_link_invoice_customer(uuid, uuid);
drop function if exists public.owner_customer_delete_blockers(uuid);

-- 4 — undo the data backfill. Order matters: release the references before
--     deleting the customers that were created for them.
update public.owner_invoices      set owner_customer_id = null;
update public.owner_payments      set owner_customer_id = null;
update public.owner_subscriptions set owner_customer_id = null;
update public.owner_expenses      set owner_customer_id = null;

-- Offers carried owner_customer_id BEFORE this migration (added 20260724120000).
-- Only clear the links this migration added: the organization-only ones.
update public.owner_offers o set owner_customer_id = null
from public.owner_customers c
where o.owner_customer_id = c.id
  and o.client_account_id is null
  and o.organization_id is not null;

-- Customers this migration CREATED. Identified by having no tasks, no activity
-- other than their creation event, and no remaining references.
delete from public.owner_customers c
where c.created_at >= '[REPLACE: migration timestamp]'
  and not exists (select 1 from public.owner_customer_tasks t where t.customer_id = c.id)
  and not exists (select 1 from public.owner_offers o where o.owner_customer_id = c.id)
  and not exists (select 1 from public.owner_invoices i where i.owner_customer_id = c.id);

-- Links this migration ADDED to the pre-existing SV Heinersreuth row.
-- Restore to the pre-migration state: both columns null.
update public.owner_customers
set client_account_id = null, organization_id = null
where id = '7b17e4a4-423a-4c60-8ff6-43187ef4d172';

-- 3/2/1 — drop the structural additions.
alter table public.owner_customers    drop column if exists archived_at,
                                      drop column if exists archived_by;
alter table public.owner_invoices     drop column if exists cancelled_at,
                                      drop column if exists cancelled_by,
                                      drop column if exists cancellation_reason;
alter table public.owner_invoices     drop column if exists owner_customer_id;
alter table public.owner_payments     drop column if exists owner_customer_id;
alter table public.owner_subscriptions drop column if exists owner_customer_id;
alter table public.owner_expenses     drop column if exists owner_customer_id;

commit;
```

`owner_list_customers` and `owner_customer_detail` are `CREATE OR REPLACE`d by
this migration and must be restored from their previous definitions in
`20260724120000_owner_customer_task_management.sql` (sections 9). Dropping the
new columns without restoring those two functions leaves them referencing
columns that no longer exist.

## What rollback cannot undo

Nothing in this migration deletes or overwrites production data, so there is no
data loss to reverse. The only irreversible act would be an **application-era**
rollback, as warned above.
